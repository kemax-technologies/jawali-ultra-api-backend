# نظام ترحيل قاعدة البيانات (Data Migration Framework) — Jawali Ultra

> **Task 11** — تم بناء هذا التوثيق بعد التحقق الفعلي من حالة الترحيلات
> الموجودة (000-007) على قاعدة بيانات الإنتاج الحقيقية (Supabase/PostgreSQL)،
> وبناء أداة تتبّع/تشغيل رسمية (`migrate.php`) واختبارها فعلياً (end-to-end)
> ضد نفس القاعدة قبل توثيقها هنا.

## 1) الوضع قبل هذه المهمة

كانت ملفات الترحيل (`000_*.sql` إلى `007_*.sql`) موجودة ومُوثَّقة جيداً في
تعليقات كل ملف، لكن **بدون أي آلية تتبّع فعلية**:

- لا يوجد جدول يسجّل "أي ملف طُبِّق، ومتى، وعلى أي قاعدة".
- التطبيق كان يدوياً بالكامل (لصق SQL في محرر Supabase أو `psql` مباشرة).
- لا توجد أداة تُخبرك "ما الترحيلات المعلَّقة؟" عند الانتقال لخادم/قاعدة
  بيانات جديدة، أو عند الشك بعد انقطاع أثناء التطبيق.
- لا توجد حماية من تعديل ملف ترحيل *بعد* تطبيقه (خطر شائع يُسبِّب عدم
  اتساق بين النسخ المختلفة من القاعدة).

**التحقق الذي أُجري (Task 11):** فحصنا قاعدة الإنتاج الحقيقية مباشرة (فحص
`information_schema` + `pg_trigger`) وتأكّدنا أن الترحيلات 000-007 مُطبَّقة
بالكامل وبشكل صحيح — كل الجداول/الأعمدة/المُشغِّلات (`triggers`) المتوقّعة
منها موجودة فعلاً. ثم سُجِّلت رسمياً في جدول التتبّع الجديد عبر
`php migrate.php backfill ...` (بدون إعادة تنفيذ SQL الخاص بها — فقط تسجيل
metadata).

## 2) الوضع الآن — الإطار الرسمي

### أ) جدول التتبّع: `schema_migrations`
أُنشئ في `008_schema_migrations_tracking.sql` ويحتوي:

| العمود        | الوصف                                                  |
|---------------|---------------------------------------------------------|
| `filename`    | اسم ملف الترحيل (فريد)                                  |
| `checksum`    | `sha256(محتوى الملف)` وقت التطبيق — لرصد أي تعديل لاحق   |
| `applied_at`  | وقت التطبيق                                              |
| `applied_by`  | `manual` (تسجيل بأثر رجعي لترحيل طُبِّق يدوياً قبل الأداة) أو `migrate_cli` (طُبِّق فعلاً عبر الأداة) |
| `execution_ms`| مدة التنفيذ بالميلي ثانية (فقط لـ `migrate_cli`)          |

### ب) أداة التشغيل: `migrate.php`
سكريبت واحد يعمل من سطر الأوامر (الاستخدام الأساسي) أو عبر HTTP (اطّلاع
فقط، محمي بمفتاح سري):

```bash
cd jawali_api
php migrate.php status              # اعرض حالة كل الترحيلات (مُطبَّق/معلَّق)
php migrate.php apply                # طبِّق كل الترحيلات المعلَّقة بالترتيب
php migrate.php backfill <file...>   # سجِّل ملفات طُبِّقت يدوياً من قبل (بدون تنفيذ SQL)
```

عبر HTTP (فقط للاطّلاع السريع عن بُعد، بمفتاح سري في الاستعلام):
```
GET /migrate.php?key=<JWT_SECRET>::migrate-status
```
(المفتاح الافتراضي = `JWT_SECRET::migrate-status`؛ يمكن تخصيصه عبر متغيّر
البيئة `MIGRATE_STATUS_SECRET` — نفس نمط `BACKUP_CRON_SECRET` في
`backup_cron.php`.)

### 🔒 قرار أمني مقصود: `apply` و `backfill` من CLI فقط
حتى مع مفتاح سري صحيح، أي طلب HTTP لـ `migrate.php` **يُعامَل دائماً كـ
`status` فقط** — بصرف النظر عن قيمة `action` المُرسَلة. تنفيذ ترحيلات
هيكلية فعلية (قد تُغيّر أو تحذف بيانات) يبقى محصوراً بمن يملك وصولاً مباشراً
لسطر الأوامر على الخادم، لتقليل مساحة الهجوم حتى لو تسرّب المفتاح السري
لاحقاً. **هذا تم التحقق منه فعلياً** (طلب HTTP بمفتاح صحيح و
`action=apply` يُعيد بيانات `status` فقط دون تنفيذ أي شيء).

## 3) قواعد كتابة ترحيل جديد

1. **التسمية**: `NNN_وصف_مختصر.sql` — رقم متتابع بـ 3 خانات (`009`, `010`, ...)،
   يُحدِّد ترتيب التطبيق (الترتيب الأبجدي = الترتيب الرقمي بسبب الحشو بالأصفار).
2. **Idempotency كلما أمكن**: استخدم `CREATE TABLE IF NOT EXISTS`،
   `ADD COLUMN IF NOT EXISTS`، `CREATE INDEX IF NOT EXISTS`، إلخ — يجعل إعادة
   محاولة تطبيق ملف فشل جزئياً أكثر أماناً، ويُبسّط الاختبار المحلي.
3. **معاملة واحدة عند الإمكان**: إن كان الملف يحتوي عبارات DDL متعددة مترابطة
   منطقياً، غلّفها بـ `BEGIN; ... COMMIT;` صريحاً بداخل الملف نفسه (مثل
   `001_multi_tenant.sql`) لضمان تراجع كامل عند أي خطأ. إن لم يحتوِ الملف على
   `BEGIN;` صريحة، فإن `migrate.php apply` يُغلِّفه تلقائياً بمعاملة واحدة.
4. **وثِّق السياق دوماً**: كل ملف ترحيل يجب أن يبدأ بتعليق يشرح: *لماذا* هذا
   التغيير مطلوب، وما المشكلة التي يحلّها — راجع الملفات 000-008 كأمثلة.
5. **⛔ ممنوع تعديل ملف ترحيل بعد تطبيقه**: إن احتجت تصحيح خطأ في ترحيل
   *مُطبَّق مسبقاً* (مسجَّل في `schema_migrations`)، **لا تُعدِّله** — أضف
   ملف ترحيل جديد يُصحِّح الأثر (مثال: `ALTER TABLE ... DROP COLUMN` ثم
   إعادة الإضافة بالشكل الصحيح). تعديل ملف مُطبَّق يُسبِّب `checksum` مختلفاً
   عن المسجَّل، وستكتشفه `migrate.php status` تلقائياً كـ"تحذير" ويرفض
   `apply` أي تنفيذ لاحق حتى تُحل المشكلة (تم اختبار هذا السلوك فعلياً).
6. **اختبر محلياً/على نسخة تطوير أولاً**، ثم طبِّق على الإنتاج عبر
   `php migrate.php apply` من سطر الأوامر على الخادم مباشرة.

## 4) استراتيجية التراجع (Rollback)

هذا الإطار **أحادي الاتجاه (forward-only) عمداً** — لا توجد ملفات
"down-migration" تلقائية. الأسباب:

- ترحيلات هذا النظام غالباً بنيوية/أمنية حسّاسة (multi-tenant، 2FA،
  immutability triggers) — تراجع تلقائي أعمى (`DROP TABLE`, إلخ) على بيانات
  إنتاج حقيقية أخطر عادةً من المشكلة الأصلية.
- بما أن كل ملف يُنفَّذ ضمن معاملة واحدة (تلقائياً أو صريحاً)، فإن **فشل
  التطبيق نفسه** يتراجع بالكامل تلقائياً (لا حالة نصف-مُطبَّقة).
- إن احتجت التراجع عن ترحيل *نجح* تطبيقه فعلاً، اكتب **ملف ترحيل جديد**
  يعكس الأثر تحديداً (نفس فلسفة "لا تُعدِّل التاريخ، أضف تصحيحاً جديداً").
